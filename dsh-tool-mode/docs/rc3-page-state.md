# RC3 — the Extensions page contradictory state

## The field contract (host → client)

The host's `describe()` row (packages/dsh-tool-mode/src/extensions-service.ts, the row
returned at the end of the per-extension describe, ≈:1719–1731) carries:

| Field | Source | Meaning |
| --- | --- | --- |
| `installed` | store record | whether bytes are installed |
| `active` | `observed?.observedActivation === 'active'` (extensions-service.ts ≈:1682, row at :1724) | the RAW lifecycle observation — it says what the store records, NOT that activation succeeded with everything prepared |
| `blocked` | `requirements.some(candidate => blocksRow(installed, candidate))` (:1707) | whether any unmet requirement blocks this row, with `blocksRow` (:166) classifying: an INSTALLED row is blocked by every unmet requirement; a NOT-installed row only by store/source/dependencies/platform/harness-model/runtime |
| `reason` | `#reasonFor` (:1734) | the highest-priority unmet blocking requirement's own wording (:1765, :1789) |
| `requirements` | per-kind list (:1376 assets, etc.) | every check with `kind`/`satisfied`/`reason`/`action` |

`readiness` is not on the row: it feeds the `assets` requirement ("activation blocked: … needs
its model assets prepared — run prepare for this extension") — which is the field the page must
gate on, not the raw `active`.

## The rendering rule (one sentence)

**A row the host reports `blocked` — or that carries any unmet requirement which blocks this
row — is never rendered as plainly "active"/ON; the badge shows "active · blocked" and the
toggle visual is OFF, while the toggle's enabled/disabled state, aria-pressed lifecycle fact and
action title are unchanged.**

## What changed

- `packages/dsh-tool-mode/src/extension-page-state.ts` (NEW): the pure, dependency-free
  derivation — `extensionPageState(row)` → `{ badge: 'not-installed' | 'active' |
  'active-blocked' | 'inactive', toggleOn, active, blocked, blockingReasons, noteReasons }` and
  `requirementBlocksRow(installed, requirement)` (mirrors the host's `blocksRow`). This is the
  contract the client bundle implements; the test pins it.
- `packages/dsh-tool-mode/client/index.template.js` (the authoritative source; the built
  `client/index.js` is regenerated by `scripts/gen-client-catalog.mjs`):
  - `extensionBadge` (:610): "active" only when active AND not blocked; "active · blocked"
    when both; "inactive" otherwise.
  - `requirementBlocksThisRow` (new, adjacent to the badge): the client-side mirror of the
    classification, used for note kinds.
  - The unmet-requirement notes loop (≈:885): a requirement that blocks THIS row renders as
    'blocker'; a post-install fact on a not-installed row (assets/executable/readiness) renders
    as a muted 'note' — so Laya's pre-install assets hint can never read as the install
    blocker, and the dependency refusal (kind `dependencies`) is the prominent blocker.
  - The toggle (`extensionRemoteRow`, ≈:919): `data-on` is ON only when active AND not
    blocked; `disabled`/`aria-pressed`/`title`/`onClick` semantics are untouched.
- No change to `extensions-service.ts` (the payload already carried every needed field) and no
  change to install/prepare/enable RPC semantics.

## Tests

`packages/dsh-tool-mode/tests/extension-page-state.test.ts`: active+blocked (embeddinggemma
shape) → "active · blocked" + toggle OFF with the lifecycle fact preserved; installed+unprepared
(host `blocked` absent but unmet assets) → still blocked; not-installed + dependency refusal →
dependencies is the blocker, the assets hint is a note; active/unblocked stays plain "active"/ON;
inactive stays OFF; satisfied requirements never block.
