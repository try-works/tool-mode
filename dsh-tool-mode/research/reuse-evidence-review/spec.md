# Adversarial review — conformance to this repository's own declarations

**Reviewer:** review-spec (adversarial). **Target:** `dsh-tool-mode/docs/reuse-evidence-plan.md` (232 lines, read in full).
**Method:** every claim below was checked against source in this tree; citations are repo-relative `path:line`.
Read-only: no source, plan or config file was modified. The plan's own numbers are quoted from its
sections; the reviewer's argument is against its mechanics, not its intent.

## 1. VERDICT

**accept-with-fixes** — the four-phase *shape* (measure signals, keep evidence, observe failures, and
only then propose) is compatible with this repository's non-goals, but five blockers must be rewritten
before it is implementable: the "local, therefore private" premise is false for the decision lane, the
lane-2 fallback contradicts SEC-10/BASE-08, the Phase-3 gate is driven by a model's preference, Phase 1
re-measures the one quantity this repo has already disproved as a correctness signal, and Phase 2's
reproducibility gate deletes exactly the evidence that blocks promotion.

## 3. WHAT BREAKS IN 12 MONTHS

- **The evidence becomes unageable.** Phase 2's observed checks are keyed to a content digest with no TTL
  and no re-verification, while the digest that renders them is capped and never expires
  (`library-digest.ts:31-40`). A year-old "5 of 12 uses" will be rendered with the same confidence as
  yesterday's, and the operator will have no way to tell. Add an `observedAt` and a staleness rule now.
- **One checkpoint silently becomes the programme's only oracle.** The same decision implementation labels
  the correction signal and (as written) judges the proposal, so a checkpoint update changes the input
  labels and the verdicts in one step, and the frozen drift set stops being comparable to the previous
  month's. The plan has no "the oracle changed" event, and no second implementation is required.
- **A second vocabulary grows beside the first.** Phase 0 introduces `no_data` as a gate outcome and
  Phase 4 introduces `no_data` again as a `wait` code for a completely different condition; neither is in
  EXT-34's management-error set (`…Spec_v1.2.md:1043`). In a year there will be three spellings of "nothing
  to do" and no registry that knows they are different.
- **The ledger's immutability is one refactor away from gone.** Phase 1's "structural, not documented"
  separation has no mechanism: this tree has no import-boundary lint rule, and the plan's own verification
  list (§8) is unit tests plus `anti_slop_lint`, neither of which can see an import. The first someone
  imports the ledger into the proposer, the boundary is gone with no failing test.
- **Every model added to a deployment becomes a new destination for operator messages.** The pass reads
  conversation text; there is no redaction step (the repo already has a credential redactor,
  `receipt.ts:188-203`, that the plan does not reuse), and no per-destination record. The next adapter
  added to the host inherits a classification path nobody re-reviewed.

## 4. QUESTIONS FOR THE LEAD

1. **Name the gate's numerator.** If wins/losses come from the blind judge, §5.3–5.4 violates
   `semantic-gate.md:26` and must be redesigned; if they come from the replay, what does the judge add, and
   may it block? The answer decides whether Phase 3 survives.
2. **Is lane 2 in scope at all?** If yes, name its config key, its default and its destination record; if no,
   delete §2.1 lane 2 and §9.1 so the plan stops pricing a consent it has not designed.
3. **Does Phase 1 still exist as a deliverable** now that `drift` is a lower bound on "not caught"? If the
   drift set is not a correctness signal, either Phase 1 becomes an evidence-count report or Phase 2 should
   come first and Phase 1 should be dropped.
4. **What may block promotion?** With `failures === 0` as the existing floor
   (`artifact-promotion.ts:202`), does an `unreproduced` failure block it? This decides whether the
   reproducibility gate is a filter or a laundering step.
5. **What is the sanctioned Phase-3 promotion path** — replays counted as uses, or `force: true`? The
   answer decides whether the plan must add a replay-counted use rule or must state the force bypass openly.
