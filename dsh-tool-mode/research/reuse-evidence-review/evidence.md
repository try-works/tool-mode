# Reuse evidence plan — adversarial review (evidence rigor and product value)

Reviewer: review-evidence. Target: `docs/reuse-evidence-plan.md` (232 lines, read in full).
Every repo claim below is checked against source; anything I could not check in this tree is
marked UNVERIFIED.

## 1. Verdict

**reject** — the programme's central predicate ("consumed, no failure class, no retry") is the
counter shape this repository has already measured and found not to be a correctness signal, its
Phase 2 adds one field of genuinely new information behind a replay that the plan's own no-values
rule forbids, and neither of its two numeric gates can fail.

## 3. What breaks in 12 months

- **The classifier lane is gated on an optional third-party extension being installed.**
  §2.1's primary lane exists "whenever the decision tools are `callable` in the catalog"
  (plan:66-68), and that is today's host state, recorded as a design premise. Uninstall the
  extension and Phase 0 does not report "no classifier" — it reports zero signals and
  "waiting for experience" (plan:31), which is the one state the plan treats as a reason to
  stop. The repo already has the right pattern for this: an unresolved provider profile makes
  a recipe tool *unavailable* rather than routable (`harness-serving.ts:170-177`). The plan
  needs the same explicit `classifier: unavailable` state or the phase will be declared
  finished by accident.
- **Evidence keyed to a digest that does not cover half the editable text.** `artifactDigest`
  is description + program + tools + inputSchema (`agent-authoring.ts:1168-1214`), while
  `purpose`, `verification` and `verifiability` sit outside it. Every future declaration
  field inherits this trap: the store accumulates evidence about text nobody serves any more,
  and the retraction rule that was supposed to prevent it cannot fire. The fix is not
  per-field patching but one rule in the digest module — "a field an agent may edit is in the
  digest, or the evidence is keyed to a digest that includes it".
- **Bounded stores that lose the record instead of saying so.** Rows evict oldest-first at 500,
  sessions at 100, failure classes at 3, receipts at 500 (`artifact-usage.ts:23-31`,
  `200-204`; `receipt.ts:34-35`). A "frozen" ledger built on this store will not report
  "the record was evicted"; it will report `insufficient` forever, and the two are
  indistinguishable — the exact defect the plan names for gates (`no regression` vs
  `no data`, plan:132-133) and then reproduces in its own storage.
- **Four stores will disagree about the same number.** `artifact-usage.json`, the
  200-receipt ring, `session-ledger.json` and the new `usage-signals` store will each hold a
  version of "how often was this used", and they already disagree internally:
  `evidence(name)` with no digest sums across every version of an artifact
  (`artifact-usage.ts:249-261`), while the digest's callers always pass one
  (`index.ts:4182-4198`). The first person to quote a number from the wrong store will be
  right about nothing, and no schema version tells them which is authoritative.
- **The one artefact that must be maintained by hand is the reference bank.** A
  pre-registered positive/negative case set has no owner in this plan and no home in this
  tree, so it will be regenerated from the current build the first time it is inconvenient —
  at which point it stops being pre-registered and the Phase 3 gate silently reverts to
  drift. Name an owner, a path, and a rule that the bank is frozen before the edit under
  test.

## 4. Questions for the Lead (each one changes the design)

1. **Is the drift set a guardrail or the acceptance reference?** If it is the reference,
   Phase 3 cannot be built on it — this tree has already measured that the counter shape it
   uses is not correctness (`research/verification-field/REPORT.md:6-8`). The answer decides
   whether Phase 1 exists at all.
2. **What is the unit of the Phase 3 gate — one signal, one artifact, one declaration field?**
   The answer fixes n, the multiplicity correction and whether a single edit may change
   `description` *and* `verification` (in which case the digest moves and the evidence
   retracts, or does not, depending on the field).
3. **Does the host have a sanctioned way to dispatch `decision_choose` for a closed session
   — which grant, which caller kind, through the DSH executor?** If not, Phase 0 needs an
   in-process classifier adapter and §2.1's "Laya first" is not available. This is the
   difference between a phase and a paragraph.
4. **May the durable usage row store the failing call's argument keys?** Paths are derived
   from the operator's own argument keys (`data-flow.ts:143-148`,
   `adoption-candidates.ts:75-86`), so this is a content decision, not a metadata one. If
   the answer is no, Phase 2 has no new content and should be deleted rather than reduced.
5. **Who owns the pre-registered reference bank, and where does it live?** Without a named
   owner and path fixed before the build, the gate cannot be audited in 12 months, and the
   plan's own claim that "an observed check is the feature" (plan:232) has nothing to check
   against.
