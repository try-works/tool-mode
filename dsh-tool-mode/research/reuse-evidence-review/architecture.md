# Reuse evidence plan — architecture review

## 1. Verdict

**Reject as written.** Phases 1 and 3 rest on three claims that are false against this host — a
"structural" proposer boundary that is a comment and is contradicted by the model-facing surface, a
per-`(name, digest)` store that cannot carry the split/freeze, and a `tools_plan` replay that the
host's own frozen-snapshot broker cannot perform — while Phase 0 is shipable once the signal source
is fixed. Cut or redefine Phase 3 and migrate Phase 1's storage claim, and this becomes
accept-with-fixes.

## 3. What breaks in 12 months

- **The artifact model only covers authored tools and workflows.** Reuse is counted by name prefix
  (`session-ledger.ts:203` on `agent_`/`workflow_`; `authoring-quality.ts:146`), and
  `receipt.artifactDigest` is attached only for authored artifacts (`index.ts:4372-4378`). Skill
  bodies, declarative recipes and extensions have no authored digest, so the second artifact class
  arrives as a second store and a second report. Introduce `ArtifactRef {kind, name, digest?,
  scopeKey}` with a resolver now; it is the only abstraction that generalises.
- **"Drift" will be searched for and the wrong 200 hits will be read.** The word already means a
  defect in the build gates; a positive signal with the same name is a permanent ambiguity.
- **Phase 4 cannot be gated, because it is not the same project.** Idle slices, yield-on-call and
  `wait` codes assume a job model the host does not have, and the budget module's own doctrine is
  that a foreground invocation is not a job and is never replayed (`harness-budgets.ts:11-12,181-192`).
  It will be rebuilt from scratch by whoever next needs it.
- **A projection bump silently deletes the signals.** `stateVersion` mismatches are ignored and
  re-folded, which is correct for a cache (`tool-insights-implementation-plan.md:368`) and wrong
  here: a signal row re-folded from a log that no longer has its receipts comes back as `null`,
  and nothing alerts. Monitoring that distinguishes null from zero is required by Phase 0's own
  rule and is not designed.
- **Artifacts get authored for the counter.** As long as the digest and `tool_mode_list` render
  `uses/failures`, the proposer optimizes them whether or not it can import the ledger; that is the
  failure `research/verification-field/REPORT.md:7-9` already recorded once (61 uses, 0 failures,
  still wrong). In a year the artifact population will encode it.

## 4. Questions for the Lead

1. Is Phase 3 in scope at all? The replay seam does not exist as specified; if it stays, who owns
   the frozen fixture broker (plugin test-only module vs a new package), and is it in Phase 3 or a
   prerequisite phase?
2. After Phase 1, which store is authoritative: a migrated `artifact-usage` (scope + per-use rows)
   or a new ledger that deprecates it? The answer decides whether Phase 1 is "M" or an "L".
3. Is lane 2 offered at all? If yes, is the classifier a declarative recipe through the existing
   broker (with the deployment's provider and journal), or a new host call path — which BASE-09
   forbids?
4. Are the usage counters allowed to stay visible to the drafting model? If not, hiding them from
   the digest and `tool_mode_list` is a product change that must be scheduled before Phase 3.
5. Who is the promotion authority: `evaluatePromotion` (uses >= 2, failures === 0), the auto-keep
   second-use rule, or the new replay gate? The plan must name one before it can claim a rollback.
